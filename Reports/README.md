# 📋 مجلد التقارير (Reports)

كل إصلاح يُنفَّذ على المشروع يجب أن يُوثَّق هنا في **ملف Markdown واحد مستقل**.
هذا المجلد هو سجل التنفيذ المقابل لخطط الإصلاح في `plans/0X_*.md`.

---

## 🏷️ تسمية الملفات

```
Reports/REP_<رقم الخطة>_<معرّف-قصير-بالإنجليزية>.md
```

أمثلة:
- `REP_02_arduino_afmotor.md`
- `REP_05_fix_emit_sensor_list.md`
- `REP_05_scenarios_case_mismatch.md`
- `REP_06_dht_integration.md`

> إذا احتاجت خطة واحدة عدة إصلاحات منفصلة، أنشئ ملف تقرير منفصل لكل إصلاح.

---

## 📝 قالب التقرير (انسخه حرفياً)

```markdown
# REP_<رقم>_<معرّف> — <عنوان الإصلاح>

- **الخطة المرجعية:** plans/0X_*.md (القسم/البند رقم)
- **التاريخ:** YYYY-MM-DD
- **المنفّذ:** <اسم الوكيل/النموذج>
- **الحالة:** ✅ مكتمل | 🟡 جزئي | ❌ محظور

## 1. المشكلة
وصف دقيق للمشكلة التي عالجها هذا الإصلاح (مع أرقام أسطر إن وُجدت).

## 2. الملفات المعدّلة
| الملف | نوع التغيير | ملخص |
|---|---|---|
| path/to/file | تعديل/إضافة/حذف | ... |

## 3. التغيير (قبل/بعد)
```diff
- الكود القديم
+ الكود الجديد
```

## 4. كيف تم التحقق
- [ ] يُترجم/يعمل (compile / run)
- [ ] اختبار يدوي: ...
- [ ] لا يكسر وظائف أخرى: ...

## 5. ملاحظات ومخاطر متبقية
أي شيء يحتاج متابعة أو قرار من المستخدم.
```

---

## ✅ قواعد إلزامية للوكلاء

1. **اقرأ قبل ما تعدّل**: الخطة المعنية + الكود الفعلي + هذا الملف.
2. **لا تخمّن العتاد**: التزم بجدول الأرجل في `plans/03_pinmap_wiring.md`.
3. **لا تكسر الشغّال**: إذا اضطررت لإزالة وظيفة، وثّق السبب في قسم الملاحظات.
4. **تقرير واحد لكل إصلاح**: لا تجمّع عدة إصلاحات غير مترابطة في ملف واحد.
5. **حدّث `Reports/INDEX.md`**: أضف سطراً واحداً لكل تقرير جديد (انظر تحت).
6. **التحقق ضروري**: لا تكتب "مكتمل" دون خطوة تحقق فعلية (compile/run/اختبار).
